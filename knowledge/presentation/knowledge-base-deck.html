Team Presentation

A Knowledge Base for Working with Claude

A persistent, file-based memory system that survives context resets - so the assistant doesn't relearn the same deployment quirk, silent failure mode, or database surprise every single session.

The Problem

Every session starts from zero

  • Context windows reset between sessions - yesterday's hard-won discovery is gone tomorrow
  • Some facts aren't in the code - external behavior, silent failure modes, "why we chose X over Y"
  • Re-deriving them costs real time - re-reading the same logs, re-tracing the same silent failure
  • Tribal knowledge lives in one person's head until it bites someone else

The Structure

One directory, four kinds of content

knowledge/ ├── CLAUDE.md # conventions & processing rules ├── learnings.md # chronological log, read every session ├── raw/ # original source dumps, verbatim ├── knowledge/ # curated pages - the actual KB │ ├── INDEX.md # tag-based navigation │ ├── gotchas.md # one-line fast-scan facts │ └── active-context.md # open tickets, in-flux areas └── experiences/ # per-session decision logs
The Core Discipline

Not everything deserves a page

"Can this fact be derived from reading the code in under 3 tool calls?"
YES → skip it
Module lists, class hierarchies, style rules - grep/find answers it faster than a stale page ever will.
NO → record it
External behavior, silent failure modes, "why" decisions invisible in the diff - these are worth preserving.
What Actually Gets Written

Category A facts only

Gotchas
One-line, fast-scan facts that bite - e.g. "DS RI plugin silently disables itself if an index is missing." Lives in gotchas.md, read first every session.
Knowledge pages
Full pages for anything needing more than 3 sentences - class hierarchies with rationale, config differences between deployment profiles.
Active context
Open tickets, areas in flux, things to watch - updated at the end of sessions touching open work.
Fragile areas
Patterns that have caused repeated failures across multiple PRs - flagged so future work in that area gets extra scrutiny.
The Loop In Action - A Real Example

Discovered once, never re-discovered

1
Discovered - 2026-06-15, PROJ-1234
The two deployment profiles route the same object types to different storage backends. In the self-hosted profile, only users and groups live in the shared store - everything else sits in the service's own repository. In the cloud profile, all of it lives in the shared store. That mismatch was the root cause of two earlier PRs scoping their plugin to the wrong backend.
2
Recorded - same session, into gotchas.md + a full backend-routing page
"Before scoping any plugin to the shared store: check the repository config for both profiles to confirm which backend each object type actually uses."
✓
Prevented - 2026-07-09, three weeks later, same ticket
Re-reading the config against the recorded rule surfaced a scope gap before it shipped: the existing integrity plugin is scoped to the service's own repository only - it does not protect data in the shared store, even though both profiles load side by side. Easy to assume coverage precisely because they load together. That gap became the justification for a new PR, opened correctly the first time.
Two sessions, three weeks apart, same open ticket - the fact recorded on day one is what caught the mistake on day twenty-four.

Staying Honest

Every page carries a trust level

✓ verified
Checked against the live codebase. Trust it.
≈ inferred
Written from exploration context, not direct verification. Confirm file paths and class names before acting.
⚠ stale
Known to need updating. Read with skepticism; update after re-verifying.
  • If a page contradicts observed reality, the page loses - update it and note the correction in learnings.md
  • Named entities (classes, files, flags) are treated as claims about the past - grep before recommending
Real self-correction, one session apart: the gotcha said RF7 block 0 "has 1 string." The next session hit a report file with an empty block 0 ([]) - the parser silently over-counted and shifted every string index. The fix (break on ]) landed in the code AND the gotcha was rewritten same-day to say "size varies, never hardcode." The KB doesn't just store facts - it gets caught being wrong and corrects itself.

When learnings.md exceeds ~20 entries, a synthesis pass distills recurring themes into permanent pages and archives the rest.

The Payoff

Small file, compounding return

  • No re-deriving - the DS RI plugin silent-disable gotcha gets caught before it burns another CI cycle
  • Faster onboarding - anyone (human or LLM) picking up this project reads gotchas.md and active-context.md first, not the whole git history
  • Self-correcting - freshness rules mean it degrades gracefully instead of silently rotting
  • Cheap to maintain - the gate keeps it small; it stays a fast scan, not a wiki nobody reads
